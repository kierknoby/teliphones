Development direction / Not a delivery promise

Earn reliability.
Then build on it.

Initial real connections matter. So does everything that happens when a session expires, a process fails or the firewall rebuilds. That is the next standard to meet.

RoadmapCurrent baselineValidation prioritiesNative terminalSupport maturityHelp with evidence

A working foundation,
not a finished assurance case.

The source implements workstation pairing, controlled WireGuard, managed certificates, health monitoring and diagnostics. Earlier operator reports include native builds, ten SSH tests, an authenticated FreePBX 17 login and owned-terminal closure on disconnect.

After 0.4.1 corrected intrusive firewall placement, FreePBX 0.5.0 adds persistent listener permissions, recovery safeguards and custom management ports. Updated Windows 0.7.0 source retains and probes the approved endpoint. These are implemented and locally tested, not planned features or proof of real-PBX readiness.

First: close the validation gaps.

Validation outstanding

Firewall coexistence on a real PBX

Verify the installed 0.5.0 broker and managed Custom Service, actual WireGuard roaming from unfamiliar public IPs, watchdog intervals and approved firewall rebuilds. Check Fail2Ban ordering and unchanged unrelated rules.

Exercise actual SIP calls, bidirectional RTP and unrelated management traffic throughout connection, rebuild, revocation and uninstall.

Validation outstanding

The entire session lifetime

Prove revocation and temporary authorisation expiry terminate owned PBX processes and leave empty cgroups, while unrelated SSH survives. Cover certificate refusal, lost reachability and client/server failure separately.

Validation outstanding

Restarts, upgrades and recovery

Test Windows/PBX reboots, broker restart, interrupted service operations, failed cleanup, upgrade, rollback and uninstall. Preserve original deadlines and an independent management route.

Validation outstanding

The real Windows and web-service matrix

Verify custom-port import, browser launch and Connection Health on native Windows, with actual Apache/TLS and redirects over WireGuard. Also check supported terminals, Unicode paths, UAC, installation, multiple users, scaling and monitor transitions. Portable build success does not replace these cases.

Planned / Not implemented

A native TELIPHONES
SSH terminal.

The intended direction is an integrated native terminal inspired by the usability of my-console: a coherent SSH experience within TELIPHONES, rather than a necessary jump to another application's window.

This is a development objective, not a feature in Windows 0.7.0. No preview screenshot, implementation deadline or finished design is claimed here.

Keep external choice

Continue to support external terminal preferences alongside the intended integrated default. Familiar tools should remain an option.

Investigate PuTTY carefully

Managed PuTTY compatibility is conditional: certificate authentication, key isolation and owned-session termination must survive intact. No password/shared-key fallback should be introduced to make it work.

Planned development direction

Remote Support and
deployment maturity.

Improve the separate support workflow through complete end-to-end testing against explicit Connect, Checker and Console implementations. Verify expiry, cleanup and firewall reachability rather than assuming workstation success proves support success.

Deployment maturity includes reviewed packages, consistent source/build provenance, clear upgrade procedures and dependable recovery. It does not imply a hosted service, an engineer portal or universal NAT traversal already exists.

Rendezvous and relay ideas are documented separately as future design. They are not connectivity capabilities in the present product.

Useful contributions
make evidence reproducible.

Record exact versions, source revisions, build identifiers, test commands and sanitised outcomes. Distinguish operator observation from independently repeatable tests. Keep screenshots genuine and free of keys or customer data.

There are no promised release dates on this page. Goals may change as testing exposes constraints. Use the repository histories and evidence register for the implemented state, not the roadmap.
