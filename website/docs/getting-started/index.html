Practical guide / My PBXs

Your first connection.
On a test system.

Start with a disposable PBX, keep an independent console route and prove each boundary before relying on the connection.

Starting sequence1. Prepare2. Install & bootstrap3. Prepare Windows4. Request & approve5. Connect6. Verify & end
01 / Establish a baseline

Prepare the PBX and network.

Use FreePBX 17 on Debian 12, with a working HTTPS administration interface and an existing root/console connection. Keep that recovery route available throughout the test.

Confirm WireGuard kernel support, systemd, Python 3 and the wg, ip, nft and iptables tools. The module can install only WireGuard tools after explicit approval; do not assume every prerequisite is supplied.

Plan a reachable WireGuard UDP endpoint, default 51821. In 0.5.0, TELIPHONES manages its FreePBX Firewall permission through a persistent Custom Service; verify generated rules without whitelisting each workstation public IP. Configure any necessary router/NAT forwarding separately. My PBXs supplies no universal NAT traversal or relay and does not close existing public management ports.

Read the platform requirements and known security limitations before changing access policy.

02 / Two installation boundaries

Module first.
Root broker second.

Obtain the trusted TELIPHONES-0.5.0.tgz test package and matching SHA-256 sidecar from the maintainer's test distribution. These files exist locally; a public download is not established. Verify the checksum before uploading through Admin > Module Admin. A source ZIP is not an installation package.

Then use Complete Installation on FreePBX 17 from an existing root shell. Use the complete procedure matching the trusted build. It stages trusted files into a root-owned location and installs the broker, SSH authority and firewall listener helper.

Repeat bootstrap after upgrading

Module Admin does not automatically update the separately installed root broker. Disconnect Windows tunnels and confirm no active support session before repeating bootstrap. Verify all three installed helpers, broker 0.5.0/protocol 6 and service restart as documented.

Refresh Connectivity > TELIPHONES and inspect System readiness. A module version or operational socket alone is not broker readiness. See package availability and verification.

03 / Set up the workstation

Keep the application
and SSH helper together.

Obtain an existing successful Windows x64 build and extract it. Keep TELIPHONES.exe beside TELIPHONES-SSH.exe. Record the source/run provenance in build-info.json.

On first launch choose applications, then reuse verified WireGuard or explicitly approve installation. UAC approval is required for tunnel setup. Refusing installation does not download anything, and you can return to Settings later.

Install Windows system OpenSSH Client if you intend to use managed SSH. Choose Windows PowerShell, PowerShell 7, Windows Terminal or Command Prompt. PuTTY is not supported for managed certificates.

04 / Exchange explicit approval

Request on Windows.
Approve on FreePBX.

  1. Choose the request type

    In Add my PBX..., enter a workstation name. Web-only is the default. Select SSH opt-in before generating the request if needed.

  2. Approve the request

    A full administrator uses Connectivity > TELIPHONES > Windows workstations over HTTPS. Paste the request, choose temporary or persistent access and enter the reachable WireGuard endpoint.

  3. Approve an account only if required

    An SSH-capable request still needs explicit SSH authorisation for an existing Linux account. There is no default root account. Leave SSH not permitted for web-only access.

  4. Import the bound response

    Paste it into the waiting Windows pairing dialog and save. Do not publish request/response strings; private keys are absent, but network metadata remains sensitive.

05 / Use the permitted services

Connect, check, then open.

Before pairing, provide the actual management services on the PBX, for example https:8443. The first entry becomes the Windows URL. Check Apache listens on the tunnel/wildcard address; permission alone does not make a service reachable. Re-pair saved profiles after URL changes.

Select the saved profile and Connect, approving local tunnel setup. Updated Windows builds check that configured TCP endpoint in Connection Health. A WireGuard handshake or successful TCP probe does not establish correct HTTP, TLS or SSH authentication.

Choose Open FreePBX and sign in normally. If explicitly approved, choose Open SSH; the app automatically requests and verifies a fresh certificate and opens the selected supported terminal.

Do not publish managed SSH or API ports to the Internet. Do not add the workstation interface/subnet to a trusted zone to get around a failure. Use the troubleshooting sequence instead.

06 / Test the end of access too

A successful login
is the beginning of validation.

Confirm that only intended services are reachable over the workstation tunnel. Compare normal SIP/RTP and unrelated management traffic before, during and after connection. Observe the actual FreePBX watchdog over multiple reported 41-second intervals, including at least five minutes of observation and approved reload testing.

Disconnect and reconnect without extending the original deadline. Close an owned terminal and observe its processes. Revoke a disposable pairing on the PBX and test temporary expiry, including the owned server cgroup and preservation of unrelated SSH sessions.

These are real-PBX acceptance tasks, not claims that the current correction has already passed them. Stop if authority extends unexpectedly, unrelated rules change or cleanup is incomplete. Do not continue on a production PBX.
